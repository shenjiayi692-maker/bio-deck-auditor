# 生物 AI 感知：里程碑与估值

> 配合 `references/common/bridge-methodology.md` 使用。心率、呼吸、血压、血氧、疾病风险和情绪不是同一难度或同一路径；逐指标、逐用途、逐辖区分析。

## 1. 指标—用途矩阵

为每个输出建立一行：输入设备、输出指标、目标人群、使用场景、医疗/非医疗用途、金标准、性能终点、现有许可和目标许可。不能用较成熟指标的证据为另一指标背书。

常见风险顺序只能作启发式：稳定条件下的心率/呼吸信号通常比无袖带血压、低患病率疾病筛查或情绪/心理状态推断更容易验证；具体结论以产品证据为准。

## 2. 监管和竞品先例

对每个先例记录监管数据库链接、编号、决定日期、产品代码、预期用途、输入方式、输出、适用人群和限制。仅有公司新闻稿或关键词结果时标为候选。

- FDA clearance、authorization 或 NMPA 注册只覆盖批文中的用途与版本，不能外推未列出的指标。
- 腕带、摄像头、接触式 PPG 和多传感器产品不可只因都叫“光学”而视为同品种。
- “未检索到”不等于全球无先例；披露数据库、检索式、日期和范围。
- 免费或低价 SDK 是价格压力线索。继续比较医疗适用范围、责任承担、集成成本、服务、数据权利和切换成本，不直接推定商业模式失效。

## 3. 医疗路线里程碑

论文/原理 → 锁定产品版本 → 外部回顾验证 → 前瞻性目标场景验证 → 注册沟通/分类 → 临床评价或试验 → 注册 → 支付/采购 → 进院 → 重复使用

机器学习性能证据应与最终部署版本一致。若 deck 只展示云端大模型，而产品销售依赖蒸馏后的端侧模型，端侧版本仍处于未验证状态。

该领域通常没有可直接复用的公开分阶段获批率。对临床、注册、采购与放量分别设置有来源的情景；没有数据时输出隐含假设，不编造精确概率或固定周期。

## 4. 收入类型

| 收入 | 核查重点 |
|---|---|
| 消费 API/SDK | 是否限制医疗声称、调用量、续费、毛利、平台依赖 |
| 医疗 API/SDK | 注册主体、许可覆盖、质量协议、变更和责任分配 |
| 硬件/模组 | BOM、良率、渠道、质保、认证和客户集中度 |
| 科研设备/项目 | 预算来源、一次性实施、可复制性和用途边界 |
| 检测服务 | 合法资质、定价/支付、金标准、复购和单位经济 |
| NRE 定制 | 验收、人力投入、知识产权和非经常性属性 |

## 5. 估值选择

| 阶段 | 方法 |
|---|---|
| 非医疗且已有重复付费 | 按软件/硬件业务拆分，核实留存、毛利和客户集中度 |
| 医疗用途、拿证前 | 里程碑情景或数据足够时 rNPV |
| 拿证后、未进院 | 采购/支付与销售 cohort 情景 |
| 已规模化 | 分部 DCF/可比，按真实收入质量校准 |

必须检查 deck 的市场故事与监管准备是否属于同一用途。若医疗 TAM 支撑估值、当前产品却只允许非医疗用途，将医疗收入列为条件情景而非基准收入。

## 6. 创始人问题

1. 每个指标在什么人群、设备、环境和金标准下验证？
2. 灵敏度、特异度、PPV/NPV、误差分布和置信区间是什么？
3. 训练、内部验证、外部验证和前瞻性验证是否严格分离？
4. 最终端侧/SDK 版本与论文版本性能差异多大？
5. 监管申报的预期用途原文、版本和编号是什么？
6. 现有收入按消费、医疗、硬件、科研、NRE 拆分后，续费和毛利如何？
7. 平台方或免费竞品出现后，哪些客户仍愿付费，原因是否被合同验证？
8. 本轮资金覆盖哪个临床、注册或商业里程碑？
