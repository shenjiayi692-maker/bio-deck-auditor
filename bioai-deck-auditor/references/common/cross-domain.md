# 跨子领域交叉:三种结构,三种估值处理

> **交叉是常态,单一子领域才是特例。**
> 大多数生物+AI公司同时横跨多个子领域:既做算法又卖硬件、既有诊断设备又有配套软件、既讲AI平台又有药物管线。
> **危险在于:机械地"把两个包相加"会漏掉最贵的错误。** 交叉有三种结构,估值处理完全不同。先判断是哪一种。

---

## 判断流程

问一个问题:**"如果业务A完全失败,业务B还有价值吗?"**

- **A失败 → B照样有价值** → **组合型(加法)**
- **A失败 → B的大部分可归属价值消失** → **依赖型(条件估值)**
- **公司在A和B之间摇摆,用一个的倍数套另一个的实质** → **伪装型(估值套利)** ← 最贵的错误

⚠️ 一家公司可能同时存在多种结构。**逐对业务判断,不要整体判断。**

---

## 结构一:组合型(加法)

**特征**:两块业务各自独立,各有各的监管路径和客户。

> 例:一家公司既卖诊断设备(器械路径),又卖配套的医院管理软件(SaaS路径)。设备卖不动,软件仍可单卖。

**估值处理:分开跑,最后相加。**
1. 业务A按其子领域的里程碑链跑一遍rNPV
2. 业务B按其子领域跑一遍
3. **不要混着算,不要用统一的折现率**——器械业务的折现率和SaaS业务的折现率不同
4. 相加得总估值

**审计要点:**
- **协同效应是真的还是讲出来的?** 公司总说"设备+软件形成闭环"。追问:有没有客户**同时买了两个**?交叉销售率是多少?如果为零,那就是两个独立生意硬拼在一起
- **资源争夺**:小团队做两条线,是优势还是分散?(见技术层"团队-技术匹配度")
- **哪块是真收入来源?** 通常一块是真生意,另一块是故事。找出来

---

## 结构二:依赖型(乘法/串联)

**特征**:B的价值以A的成功为前提。**A的失败概率必须乘进B。**

> 例1:AI制药公司的"算法平台"。平台的价值主张是"能更快发现好药"——但这个主张**只有在管线成功后才被验证**。管线全灭,平台的价值主张就没了(至少在证明之前不能按已验证来估)。
>
> 例2:一家做手术机器人的公司,同时卖"手术数据SaaS"。SaaS的数据来自机器人。机器人卖不出去 → 没有数据 → SaaS无从谈起。

**估值处理:概率连乘,不是相加。**
```
B的期望价值 = B的成功后价值 × P(A成功) × P(B|A成功)
```

**审计要点——这是最容易被高估的结构:**
- **公司会把两块的价值分别讲一遍,让你以为是加法。** 实际是乘法。这个偷换能把估值放大数倍
- 明确问:**"如果管线/主产品失败,这个平台/SaaS还值多少钱?"** 如果答案是"接近零",那它就不该被独立计价
- **反向检验**:平台如果真的独立有价值,**为什么没有第三方付费使用?** 有外部客户就是加法,没有就是乘法

---

## 结构三:伪装型(估值套利)★ 最贵的错误 ★

**特征**:公司的**业务实质**是X,但用**Y的估值逻辑**融资。它在两个身份之间摇摆,哪个对它有利用哪个。

### 最典型:AI制药(TechBio)的双重身份

| 身份 | 估值逻辑 | 倍数量级 |
|---|---|---|
| **"我们是更快的药企"** | 管线 rNPV（按匹配的临床阶段数据折算） | 受制于管线特异的临床与商业风险 |
| **"我们是卖铲子的平台"** | SaaS/平台倍数(按ARR给PS) | 高得多 |

**套利手法**:
- 融资时讲**平台故事**(要SaaS的高倍数)
- 被质疑管线进展慢时说**"我们是药企,要看长期"**(躲开SaaS的增长要求)
- **两个身份的义务都不承担,两个身份的溢价都想要**

**破解方法:逼它选边。**

问三个问题,答案会暴露实质:
1. **平台有没有第三方付费客户?** 有真实的、非关联方的、重复付费的平台客户 → 它可能真是平台。只服务自己的管线 → 它是药企,平台是内部工具
2. **收入结构是什么?** 平台收入(订阅/服务费)占比多少?里程碑付款和license-out占比多少?**后者是药企的收入形态**
3. **如果所有自有管线都失败,平台还有人买单吗?**

> **判定**:
> - 若“平台”只服务自己的管线 → 平台独立商业价值尚未验证；先按管线 rNPV 估值，平台对速度、成本或成功概率的贡献只有在可比证据支持时才单列
> - 若有真实的第三方平台收入 → 可以拆成"平台业务(SaaS估值)+ 自有管线(rNPV)",按**组合型**相加
> - 若两者都不成立（平台无客户、管线尚早）→ 采用早期期权或融资里程碑法，不同时给予平台与成熟管线溢价

### 其他常见的伪装型

| 伪装 | 实质 | 破解 |
|---|---|---|
| "AI算法平台"可能实为**硬件/交付业务** | 毛利与收入结构存在张力 | 拆分收入、直接成本和人力投入 |
| "医疗器械公司"实为**项目制外包** | 每个客户都要定制NRE | 看收入的可复制性 |
| "健康消费品"蹭**医疗溢价** | 不做医疗声称,却按医疗估值 | 它担医疗责任吗?不担就不该拿溢价 |
| "SaaS"实为**卖软件许可** | 一次性收入伪装成经常性 | 看续费率 |

## ★ 混合公司的估值:模型怎么选、占比怎么定 ★

**这是交叉审计里最实操、也最容易做错的一步。** 器械+SaaS、算法+硬件、平台+管线,都要回答同一个问题:**用哪个模型?各占多少?**

### 第一步:先定结构,再谈占比

**占比只在"组合型(加法)"下才有意义。**
- **依赖型**:不存在"占比",B的价值整体乘以A的成功概率。**如果你在给依赖型分配占比,你已经错了**
- **伪装型**:不存在"占比",要先破除伪装,定出它到底是哪一个,再估
- **只有组合型**,才需要往下走"权重"的问题

### 第二步:组合型的分部估值(SOTP)

按业务分部,每部分**独立**选模型、独立选折现率,最后相加:

```
公司估值 = Σ (各业务分部的独立估值) - 未分摊的公司层面成本(总部、研发、股权激励)
```

| 分部性质 | 用什么模型 | 折现率 |
|---|---|---|
| 已拿证 / 已放量的医疗业务 | DCF 或 可比公司 | 正常 |
| 未拿证的医疗业务 | **rNPV**(分阶段风险调整) | 高(生物科技级) |
| 消费/非医疗软件业务 | SaaS倍数(看ARR、留存、毛利) | 中 |
| 硬件业务 | 硬件公司倍数(**注意:毛利决定倍数,不是故事决定**) | 中 |
| 纯定制开发/NRE | **项目制/人头制估值**(最低倍数) | 中 |

**⚠️ 最常见的错误:用一个统一的估值倍数套整个公司。** 一家60%毛利的公司,如果其中40%收入是90%毛利的软件、60%是40%毛利的硬件,**这两块必须分开给倍数**,否则你要么高估了硬件,要么低估了软件。

### 第三步:占比怎么定?——用三种口径交叉验证

**不要只看deck给的收入占比。** 用三个口径同时看,不一致处就是问题所在:

| 口径 | 怎么算 | 揭示什么 |
|---|---|---|
| **① 收入占比** | 各分部收入 / 总收入 | deck最爱给这个。**但收入占比≠价值占比** |
| **② 毛利占比** | 各分部毛利 / 总毛利 | **比收入占比更接近真实价值贡献**。一个占收入60%但毛利只有20%的硬件业务,价值贡献远低于它的收入占比 |
| **③ 资源投入占比** | 人力/研发投入分布 | 揭示公司当前主要执行重心；与融资叙事不一致时需要解释 |

**交叉验证的用法:**
> **若 ①收入占比 与 ③投入占比 严重背离** → 公司在**用一块业务的收入,补贴另一块业务的故事**。
> 例:算法收入占10%,但80%的融资故事和50%的人力在讲算法 → **这家公司实质是硬件公司,在补贴一个还没验证的算法梦。** 估值应按硬件给,算法作为期权额外计价(而非作为主体)。

**若 deck 只给收入占比不给毛利拆分** → 索取分部毛利。未提供时标为估值证据缺口；结合公司阶段和财务成熟度决定严重度。

### 第四步:检查"协同溢价"是真的吗?

混合公司总说"1+1>2"。**验证方法:**
- **交叉销售率**:有多少客户同时买了两块业务?零交叉销售削弱商业协同证据，但早期产品也可能尚未开始交叉销售；继续检查技术、渠道和数据复用
- **技术复用率**:两块业务真的共用同一套核心技术吗?还是各做各的?
- **反向检验**:如果把两块业务**拆开卖**,加起来值多少?如果拆开更值钱,那"协同"是负的

### 一个完整的示例(器械+SaaS)

> **公司**:卖诊断设备(未拿证),同时卖配套医院数据SaaS(数据来自设备)
>
> **① 结构判定**:SaaS数据全部来自设备 → 设备卖不动则SaaS无数据 → **依赖型(乘法),不是组合型**
>
> **② 因此不谈占比**:SaaS的期望值 = SaaS成功后价值 × P(设备成功)
>
> **③ 设备的 P**：未拿证，剩余关卡（前瞻验证→受理→拿证→支付/采购→进院）分别设概率，并展示来源与敏感性
>
> **④ 结论**:
> - deck的做法:器械市场X亿 + SaaS市场Y亿,**相加** → **结构性错误**
> - 处理方式：器械 rNPV + SaaS 条件价值 × P（硬件达到依赖里程碑）；P 不足时只展示情景
> - **deck的加法把总估值放大了约 (X+Y) / (X_rNPV + 0.2Y) 倍**
>
> **⑤ 若SaaS有独立的第三方客户**(数据不依赖自家设备)→ **结构改判为组合型**,才可以分部相加。**这个判定值多少钱,取决于有没有那几个独立客户。**

## 交叉时的监管处理(常被漏掉)

**多个业务 = 多条监管路径,而且它们可能互相污染:**

1. **最严的那条决定整体**:如果软件模块被认定为器械的一部分,整个产品可能都要走器械注册
2. **"临床决策支持"是SaaS变器械的常见触发点**:一个医院管理SaaS,一旦开始给临床建议,可能就越界成了器械
3. **硬件+软件的组合注册**:软硬一体的产品,注册的是整体还是分开?这决定了迭代的自由度
4. **一条线的合规问题会拖累另一条**:如果器械业务因无证被查,SaaS业务的客户(医院)也会受影响

**审计动作:把公司的每个产品/模块单独做一次"这是不是医疗器械"的判定**(见 `audit-regulatory-common.md`),不要只判定主产品。

## 报告里怎么写交叉

在报告的"桥接估值"一节,**显式说明交叉结构**:

> **示例写法**
> "本公司横跨器械与SaaS两个子领域,但两者是**依赖型(乘法)**而非组合型:SaaS的数据全部来自其硬件设备,硬件不放量则SaaS无数据可用。
> deck把两块业务的市场空间分别列出并相加(器械X亿 + SaaS Y亿),这在结构上是错的——**SaaS的期望值必须乘以硬件成功的概率**。
> 按硬件当前监管阶段，将 SaaS 价值乘以各依赖里程碑的条件概率；若概率缺少数据，报告悲观/基准/乐观情景，不给虚假的单点放大倍数。"

**这段话是通用财务工具永远给不出的。它同时用到了:子领域判定 + 交叉结构判定 + 监管阶段定位 + 概率连乘。**
